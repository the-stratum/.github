# Security Policy

STRATUM takes the security and privacy of its projects, contributors, and users seriously.

We welcome responsible security research that helps identify and address vulnerabilities in our software, infrastructure, and services.

## 1. Reporting a Vulnerability

**Please report security vulnerabilities privately. Do not disclose suspected vulnerabilities through public GitHub issues, pull requests, discussions, or community channels.**

Use one of the following methods:

### GitHub Private Vulnerability Reporting

Where a repository has GitHub Private Vulnerability Reporting enabled, use its **Report a vulnerability** option to submit your report securely.

### Email

If private vulnerability reporting is unavailable, contact:

**stratum027@gmail.com**

Suggested subject:

`[SECURITY] Repository Name – Brief Vulnerability Summary`

Please include enough information for the maintainers to understand, reproduce, and assess the issue.

## 2. Information to Include

A useful report should include, where possible:

- A clear description of the suspected vulnerability.
- The affected repository, component, and version or commit.
- Steps to reproduce the issue.
- The potential security impact.
- Proof-of-concept material, if safe and necessary.
- Relevant logs, screenshots, or technical details.
- Any suggested mitigation or remediation.

Please redact passwords, API keys, access tokens, personal information, and other sensitive data before submitting a report.

## 3. Responsible Disclosure

We ask security researchers to:

- Allow maintainers reasonable time to investigate and address the issue.
- Avoid public disclosure before coordinating with the maintainers.
- Share technical details only with people who need them to investigate.
- Coordinate an appropriate disclosure plan with the maintainers.
- Avoid actions that could expose users or systems to additional risk.

We will handle reports in good faith and aim to communicate clearly throughout the process.

Response and remediation timelines may depend on the issue's severity, complexity, and available resources.

## 4. Scope and Testing Restrictions

Security testing must be limited to systems and environments that you own or are explicitly authorized to test.

Do not:

- Access, modify, delete, or extract data belonging to other users.
- Disrupt services or degrade availability.
- Attempt persistent access or deploy malicious software.
- Conduct social engineering or phishing attacks.
- Test third-party services or infrastructure without authorization.
- Use a vulnerability to access information beyond what is necessary to demonstrate the issue safely.

Stop testing once you have obtained sufficient evidence to demonstrate the suspected vulnerability.

## 5. Security Research and Good Faith

We appreciate responsible security research conducted in good faith.

Researchers should follow applicable laws, respect user privacy, and avoid causing harm.

Nothing in this policy grants authorization to test systems or services that you do not own or have explicit permission to assess.

## 6. Rewards and Recognition

STRATUM does not currently promise monetary rewards, bug bounty payments, or other compensation for vulnerability reports.

Recognition may be considered with the researcher's consent and where appropriate.

## 7. Supported Versions

Individual repositories may define their own supported versions and security-maintenance policies.

Where a project provides a repository-specific security policy, that policy takes precedence over this general organization-wide guidance.

Researchers should include the affected version or commit in their report so maintainers can assess the issue accurately.

## 8. Final Notes

Security reports are handled according to the nature and severity of the reported issue.

Submitting a report does not guarantee that a vulnerability will be confirmed, that a fix will be released, or that a particular response timeline will be met.

Thank you for helping STRATUM build safer and more reliable software.
