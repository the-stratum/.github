# Contributing to STRATUM

Thank you for your interest in contributing to STRATUM.

STRATUM is an independent engineering and creative collective focused on building software, developer tools, digital experiences, infrastructure, automation, and creative technology.

We welcome thoughtful contributions that improve the quality, reliability, security, and usability of our projects.

## 1. Before You Contribute

Before starting work:

- Read the target repository's README and available documentation.
- Check existing issues and pull requests to avoid duplicated work.
- Review the project's license and contribution requirements.
- For significant features, architectural changes, or proposed dependencies, open an issue or discussion before implementation.

Each repository may have additional project-specific requirements. Those instructions take precedence where applicable.

## 2. Ways to Contribute

You can contribute through:

- Bug reports and reproducible problem descriptions.
- Feature proposals and improvements.
- Code, documentation, and UI/UX changes.
- Testing, quality assurance, and performance improvements.
- Security and accessibility improvements.
- Infrastructure, deployment, and automation improvements.

Contributions should be relevant to the project and supported by a clear explanation.

## 3. Development Workflow

For repositories where you have write access:

1. Start from the latest `main` branch.
2. Create a separate branch for your work.
3. Make focused changes related to one objective.
4. Test your changes using the project's available instructions.
5. Commit your work with a clear and meaningful message.
6. Open a pull request against the appropriate base branch.

External contributors should fork the repository and submit a pull request from their fork where applicable.

Never make direct changes to a protected `main` branch.

### Branch naming

Use descriptive branch names. Suggested prefixes include:

- `feature/` — new functionality
- `fix/` — bug fixes
- `docs/` — documentation
- `refactor/` — code restructuring
- `security/` — security improvements
- `maintenance/` — maintenance work

Example: `fix/dashboard-authentication`

## 4. Commit Guidelines

Write clear commit messages that describe the purpose of each change.

Examples:

- `docs: update installation instructions`
- `fix: handle invalid configuration`
- `feat: add server analytics`
- `refactor: simplify permission checks`

Keep commits focused and avoid combining unrelated changes.

## 5. Pull Request Guidelines

Every pull request should:

- Explain what changed and why.
- Reference related issues where applicable.
- Describe important implementation decisions.
- Include testing performed and its actual results.
- Identify breaking changes or compatibility concerns.
- Include screenshots for relevant visual changes.
- Mention security and privacy implications where relevant.

Keep pull requests focused and reasonably sized.

Do not claim that tests passed unless they were actually executed.

A pull request may be reviewed, requested for changes, or declined when it does not meet the project's requirements.

## 6. Code Quality

Contributions should follow the conventions and architecture already established by the target project.

We encourage contributors to:

- Prefer straightforward, maintainable implementations.
- Avoid unnecessary dependencies and complexity.
- Handle errors and unexpected inputs appropriately.
- Consider performance, accessibility, and compatibility.
- Update relevant documentation when behaviour changes.
- Include or update tests where appropriate.

Do not introduce unrelated changes or rewrite existing functionality without a clear reason.

## 7. Security and Privacy

Security is a shared responsibility.

- Never commit API keys, access tokens, passwords, private keys, or other credentials.
- Do not include sensitive personal information in source code, issues, or logs.
- Use environment variables and documented secret-management methods.
- Provide placeholder values in `.env.example` files.
- Review dependencies and external integrations before introducing them.
- Do not publish details of an exploitable vulnerability in a public issue.

Use an appropriate private reporting channel for sensitive security concerns.

## 8. Third-Party Code and Assets

Contributors must have the right to submit the code, documentation, designs, and other assets they provide.

Respect the licenses, attribution requirements, and usage restrictions of third-party materials.

Do not introduce copied, proprietary, or unlicensed material into a project.

## 9. Communication and Collaboration

We expect all contributors to communicate respectfully and constructively.

- Keep discussions relevant and technically useful.
- Provide clear explanations and reproducible examples.
- Accept constructive feedback professionally.
- Disagree with ideas respectfully.
- Avoid spam, harassment, and disruptive behaviour.

Good collaboration matters as much as good implementation.

## 10. Final Notes

Contribution does not guarantee acceptance or immediate review.

Project maintainers make decisions based on project scope, technical quality, maintainability, security, and available resources.

Thank you for helping STRATUM build better things.
